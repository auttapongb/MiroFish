# MiroFish — Output Interpretation Manual

> **Scope:** What every screen and field in MiroFish means, for the person *running* the sim (you) and for *end users* who just want the result.
> **Grounded in:** the actual backend code (`oasis_profile_generator.py`, `simulation_runner.py`, `report_agent.py`, `graph_builder.py`) — not guesswork.

---

## 0. The 5-step pipeline (what you're watching)

| # | Step | What happens | What a user *needs* to see |
|---|------|-------------|----------------------------|
| 01 | **Reality Seed** | You upload the source doc (personas) | "your files are in" |
| 02 | **Graph Build** | Doc is chunked → Zep extracts entities/relations into a knowledge graph | "analyzing your data…" |
| 03 | **Env Setup** | Entities → agent personas + config | "building the world…" |
| 04 | **Simulation** | Agents act in rounds (posts, comments, follows) | "simulating…" |
| 05 | **Report** | ReportAgent reads the sim + writes the report | "**here's your report**" |

**Key principle:** steps 01–04 are *means*; step 05 is the *deliverable*. An end user only needs to know "it's working" + "it's done." Everything below is for the operator (you) or advanced users.

## 1. Step 02 — Graph Build output

### What you see in the SYSTEM DASHBOARD

```
Zep processing... 20/40 done, 20 pending (849s)
```

| Term | Meaning |
|------|---------|
| `40` | **Text chunks** — your seed doc split into ~500-char pieces (NOT personas, NOT rounds) |
| `done / pending` | How many chunks Zep has finished extracting |
| `(849s)` | Seconds elapsed since the batch was submitted |

### The metrics cards

- **ENTITY NODES** — distinct "things" Zep found: people (Person), orgs (Company), places, groups (Worker), etc.
- **RELATION EDGES** — how those entities connect (e.g. "Jinda — works_with → Somchai").
- **Third metric** — usually community summaries / graph size.

> ⚠️ **"57 agents but I wrote 30 personas?"** — Zep's entity count is *non-deterministic* (it over-splits names, adds orgs/places). The **final agent count is re-anchored to your `### N. Name — Role` headings**, so you get exactly 30. The "57" is a raw intermediate, discarded later.

## 2. Step 03 — AGENT CONFIG output

Each agent gets an **OASIS profile** (schema from the OASIS engine, `camel-ai/oasis`). Fields:

| Field | Meaning | End user cares? |
|-------|---------|-----------------|
| `user_id` | Numeric agent ID | No |
| `user_name` | @handle | No |
| `name` | Display name | Yes (who's in the world) |
| `bio` | Short self-description | Maybe |
| `persona` | Full character prompt → **drives behavior** | No (internal) |
| `karma` | Reddit-style reputation | No |
| `friend_count` / `follower_count` / `statuses_count` | Twitter-style social metrics | No |
| `age` / `gender` / `mbti` / `country` / `profession` | Demographics + psychographics | Maybe |
| `interested_topics` | Topics the agent engages with → **determines what they post about** | Yes (understandable) |
| `source_entity_uuid` / `source_entity_type` | Which Zep graph entity spawned this agent | No |
| `created_at` | Account creation date | No |

### The "474 related topics" number
That's the **sum of all `interested_topics` lists across all agents** (not unique topics). 57 agents × ~8.3 topics avg = 474 total topic slots.

## 3. Step 04 — SIMULATION output

### Rounds
- `total_rounds` = your **duration setting** (e.g. 12 months @ weekly = **48 rounds**). 1 round = 1 week (your convention).
- `current_round` / `progress_percent` = how far along it is.

### Agent actions (per round)
Agents act on two platforms (Twitter + Reddit). Action types from the OASIS engine:

| Action | Meaning |
|--------|---------|
| `CREATE_POST` | Agent wrote a new post |
| `CREATE_COMMENT` | Replied to someone |
| `LIKE_COMMENT` / `DISLIKE_COMMENT` | Reacted |
| `FOLLOW` / `MUTE` | Changed their network |
| `SEARCH_POSTS` / `SEARCH_USER` / `TREND` | Browsed/explored |
| `REFRESH` | Pulled their feed |
| `DO_NOTHING` | Sat the round out |

Each round also produces a **RoundSummary** (what happened that week) and updates **temporal memory** (Zep graph — who's connected to whom now).

## 4. Step 05 — REPORT output

The report is generated by **ReportAgent** (a tool-using agent that queries the post-sim environment). Typical structure:

1. **Executive summary** — the headline prediction/outcome.
2. **Narrative / timeline** — how events unfolded over the rounds.
3. **Agent / faction analysis** — what each camp did and why.
4. **Key turning points** — which actions/rounds changed the trajectory.
5. **Recommendations / implications** — what it means for your decision.
6. **Plain Language Summary** — the "for dummies" takeaway (TL;DR).

> Sections are scenario-dependent (the LLM tailors them to your prompt), but the above is the standard shape.

---

## 5. Step 05 — INTERACTION output

After the sim, you can **chat with any agent** (ask a persona its opinion) and **converse with ReportAgent** (ask follow-ups on the report). This is where the "deep interaction" happens.

---

## 6. The UX question: what should end users actually see?

**They should NOT see the technical internals.** An end user wants:

1. **Progress** — "Step 2/5 — analyzing your data… 60%" (not "Zep processing 20/40 done (849s)").
2. **The report** — the prediction + plain-language summary.
3. **Optional** — chat with the agents.

Everything else — the SYSTEM DASHBOARD log, batch IDs, entity/edge counts, raw AGENT CONFIG fields, `karma`/`mbti`/`source_entity_uuid` — is **debug/operator noise** and should live behind an "Advanced / Developer" toggle.

### Recommended UX split

| Mode | Shows |
|------|-------|
| **Simple (default)** | Clean 5-step progress bar + report + chat. No raw logs, no field dumps. |
| **Detail (power user)** | Everything above (current behavior) — for you to debug runs. |
